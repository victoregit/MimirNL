# Security model and limits

Mimir is a trusted local single-user process, not a multi-tenant authorization server. Project UUID selection enforces application data isolation; anyone with filesystem access to the database can read it directly. MCP clients are trusted to forward actual user approval, rather than invent approval flags. Use host tool approval controls for registration, verification, sharing and deletion. There is no remote listener or network code in the application.

Inputs are untrusted data, including file names, documentation, commits, source references, observations and feedback. Whole requests are screened before schema validation/persistence. Imported content has explicit untrusted labels and is never interpreted as instructions, scripts, SQL or authorization. SQL values are prepared; only fixed allowlisted filter column names are composed. Files are read through canonical paths; symlinks and external Git metadata/config are rejected. Git runs with argument arrays, time/output bounds and hooks/fsmonitor disabled. No checkout, fetch, project hooks, filters, package scripts or test execution occurs.

Path exclusions cover `.env*`, `.ssh`, `.aws`, credentials, PEM files, `.npmrc`, `.netrc`, private-key basenames, dependencies and build outputs. Custom excludes are case-insensitive literal path substrings, not glob patterns. Optional bounded `includes` entries are relative file/directory prefixes (case-insensitive); default deny rules still apply. An include policy disables commit-message import because messages are not confined to file prefixes. Gitignore excludes both tracked and untracked matching paths; security exclusions apply independently. Submodule directories are not traversed. A NUL byte marks binary data. Text above the per-file bound is skipped. Sensitive fixtures contain placeholders; tests do not read real credential files.

The secret detector rejects common private-key headers, AWS access-key IDs, GitHub/OpenAI-style tokens, bearer/JWT forms and password/key/token assignments. It checks all submitted fields, commit metadata and candidate file content before persistence. This is heuristic: unknown, encoded, fragmented, obfuscated or innocently named credentials can evade it; false positives are possible. Do not ingest repositories containing secrets. Review allowed sources and stored data. There is no claim of exhaustive DLP, sandbox isolation from a malicious local filesystem race, or cryptographic protection. Git and Node binaries on PATH must be trusted. The adapter rejects known unsafe repository configurations but does not sandbox the Git executable.

POSIX database creation uses 0600 before WAL creation; new data directories use 0700. Existing parent directories remain operator-owned. Windows requires operator-configured private ACLs. Keep the DB outside analyzed repos and version control, on local storage with sound SQLite locking. Symlinked database files are rejected. Avoid simultaneous Windows/WSL access and network filesystems. Backups contain the same private data as the database.

Deletion requires `confirm: true`, removes local memory/project rows, dependent history/feedback/relations/metrics and FTS entries transactionally, and never deletes source repository files. Shared copies survive source-project deletion; delete them explicitly using scope global and sharing approval. SQLite pages, WAL files, backups and filesystem snapshots may retain recoverable historical bytes. Logical deletion is not secure erasure. Stop clients before manual maintenance; supported online [backup/restore](backup-restore.md) captures consistent committed WAL state without stopping writers. Use OS-supported secure disposal where required. Retrieval aggregate records may survive individual-memory deletion.

Search/get/stats require project selection. Private relations cannot cross projects. Global promotion strips source IDs/paths but cannot remove project identifiers embedded in the approved content. Global content is independent, deliberately shared data. Do not approve sharing without reviewing it. No security review has been self-approved; independent review remains required.

See the root [security policy](../SECURITY.md) for reporting and detailed retention boundaries.

`includes` defines the active file set for reconciliation, rather than an append-only import filter. For example, after a full ingest, ingesting with `includes: ["docs"]` deprecates previously imported file memories outside `docs`. A later full ingest reactivates those files as `candidate`, including previously verified files; approval must be renewed. Commit messages are not imported with an include policy.
